bot_v168_clean_core_record_identity

1. Неизменяемая идентичность финансовых записей
- Каждая ARS/USD запись получает record_uid (12 hex), который не меняется при перенумерации R/U.
- Новая команда бот-копии: /izm_R60_uXXXXXXXXXXXX. R60 остается только человекочитаемым номером.
- После изменения порядка записей R60 может стать R61, но uXXXXXXXXXXXX остается тем же и открывает ту же запись.
- Старые команды вида /izm_R60 без UID больше не ищут запись по текущему R60: они fail-closed и показывают предупреждение, чтобы не открыть чужую операцию.
- Предварительное угадывание /izm_Rxx до создания финансовой строки отключено. Команда появляется только после наличия строки и локального SQLite commit.
- На старте v168 UID добавляются существующим записям; после миграции запрашивается полный snapshot.

2. Защита пересланной финансовой операции
- Связанная финансовая строка сохраняется в SQLite до публикации активной /izm-команды/кнопки на бот-копии.
- /izm_ теперь классифицируется как открытие редактора, а не как новая финансовая mutation-команда; ложные durable needs_review для самого клика убраны.
- Delta record key использует record_uid, а не изменяемый R/id при его наличии.

3. MEGA delta hardening
- Большие журналы ТЗ/маркировок окон исключены из каждой финансовой delta; они остаются в SQLite/full snapshot.
- Несколько больших root-словарей переведены на entry-level map delta вместо пересылки целого словаря при одном изменении.
- Истории gomonk-rebalance исключены из chat settings delta, текущее состояние резервов сохраняется.
- Цель: убрать повторяющийся oversized compact delta, который в v167 доходил примерно до 670 KB и мешал durable-подтверждению финансов.

4. Ф2 — доступ владельца к чатам
- Восстановлен реальный переключатель доступа владельца.
- Добавлены 1-й и 2-й круг по той же модели, что меню пересылки/финрежима.
- Включение относится к конкретному чату. В выбранном чате именно основной владелец бота может пользоваться owner-функциями для просмотра/проверки; остальные пользователи чата не становятся владельцами.
- Выбор хранится в owner_access_chat_ids_v168 и не смешивается с legacy additional_owner_ids.

5. Ф91 — быстрое обновление
- После фактического добавления финансовой записи строка сразу фиксируется в локальном SQLite и запускается обновление Ф91 до тяжелых root/MEGA операций.
- Быстрое обновление также запускается после финансовой пересылки, ручного редактирования и удаления.
- Несколько сигналов одной операции коалесцируются в одно обновление примерно через 10 мс.
- Старые параллельные Ф91 остаются рабочими, но автоматом обновляются только активные и недавно использованные окна (по умолчанию 15 минут). Это предотвращает десятки Telegram edit на одну транзакцию при накопившихся старых окнах.

6. Кнопки/окна
- register_open_window/unregister_open_window больше не делают синхронный полный root save в callback-потоке; запись реестра отложена в config-io.
- Убран неиспользуемый v163 WINDOW_UI_TASK_POOL: вместо трех мертвых worker-потоков используется существующий UI pool до загрузки активного v166 router.
- Эфемерное 40-секундное состояние редактирования бот-копии больше не сохраняется тяжелым root save.

7. ТЗ окон
- После restore v168 старые open-ТЗ действительно проходят post-restore rollover.
- Два ТЗ из v167, реализованные этой версией (Ф2 переключение владельца и быстрое Ф91), помечаются fixed с fixed_by_version=v168.
- Остальные старые open-ТЗ архивируются, но не объявляются исправленными.
- Текущий список ТЗ v168 начинается чистым.

Схема данных не ломает старые backup: restore принимает v153-v168. Старые /izm_Rxx намеренно не переназначаются на текущие Rxx, потому что это могло бы открыть неправильную запись.
